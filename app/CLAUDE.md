# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
# Build debug APK (first build fetches Oboe 1.9.0 from GitHub via CMake FetchContent — needs internet)
./gradlew :app:assembleDebug

# Unit tests (currently only placeholder tests exist — ExampleUnitTest.kt)
./gradlew :app:test

# Instrumented tests (needs a connected device/emulator — currently only a placeholder)
./gradlew :app:connectedAndroidTest

# Lint
./gradlew :app:lint
```

Requires: Android Studio or standalone SDK, **NDK 27.0.12077973 exactly** (pinned in `build.gradle.kts` — a different NDK version can produce subtly different native behavior for the audio engine), CMake 3.22.1, JDK 21. `local.properties` with `sdk.dir=...` must exist (not checked in).

There is no separate lint config beyond the Android Gradle plugin default — `app/src/main/keepRules/rules.keep` (R8/ProGuard) is currently empty and release optimization is disabled in `build.gradle.kts`.

## Architecture

Single Activity (`MainActivity`), no ViewModel/Hilt/Navigation component. Everything is state-driven Jetpack Compose. `ui/OctapadScreen.kt` (~2100 lines) owns nearly all UI state directly as `remember { mutableStateOf }` / `SnapshotStateList`; a handful of singleton objects hold state that needs to outlive recomposition (`AudioRepository`, `KitRepository`, `PreferencesRepository`, `DrumEngine`, `PadDurationCache`, `MidiEventBus`, `CcMapRepository`, `MidiLearnRepository`, `MidiChannelState`, `NativeBridge`, and the `license/` package's `LicenseRepository`/`LicenseApi`/`DeviceId`). `MidiLearnRepository` holds note-based pad mapping and is still live — see the MIDI section below.

**App entry gate** (`MainActivity.kt`): Splash screen → one-time "follow us" social-links screen (`SocialLinksScreen`, gated on `PreferencesRepository.hasSeenSocialLinks()`, shown once per install — placeholder YouTube/Instagram/WhatsApp URLs at the top of `SplashScreen.kt`, replace before shipping) → activation gate (blocks until `LicenseRepository.isUsable()`, which has a 3-day offline grace period) → `OctapadScreen`. `OctapadScreen` re-checks license status with the admin panel every 30 minutes while open.

**Right-panel layout** (`ui/RightPanel.kt` + `ui/EQPanel.kt` + `ui/TempoPanel.kt` + `ui/ChokePanel.kt` + `ui/DelayPanel.kt`): five groups. Main display (`RightPanel.kt`'s own column — EDIT/SAVE/LOAD quick buttons, Volume/Pitch, bank A/B, Patch List nav, kit name) stays in the main column — Bank C no longer exists, see below; **FX** (`EQPanel.kt`, header text says "FX") holds EQ, Reverse, Pan, Gain, Velocity, Recording, and a one-tap "IMPORT TO THIS PAD" button — Delay does **not** live here (see DELAY below; an earlier version of this doc said Delay was merged into FX from a standalone panel that "no longer exists" — that's stale, `DelayPanel.kt` exists again as its own top-level panel); **CHOKE** (`ChokePanel.kt`, its own top-level button next to CROP/DELAY) holds the Exclusive Mode toggle, the ACTIVE LEVEL selector (None/1/2/3/4, trimmed from 6 — see the choke-redesign note below), and per-level pad-membership as 4 collapsible folders; **DELAY** (`DelayPanel.kt`, its own top-level button next to CROP/CHOKE) holds a MASTER on/off kill switch plus the per-pad DELAY on/off toggle, DLY TIME, DLY LEVEL, and the "apply to" pad picker — moved back out of FX into its own dedicated panel (see the delay-panel note below); **LOOP** (`TempoPanel.kt`, header text says "LOOP") holds BPM, the SPEED multiplier, the global LOOP toggle, a CHOKE quick-toggle (same Exclusive Mode state `ChokePanel.kt` uses — live-performance shortcut only, detailed level/group assignment still lives in the CHOKE panel), and per-pad PLAY MODE (ONE SHOT/LOOP/MULTIPLAY — MULTIPLAY is the old "MIX" mode, just relabeled). Metronome and the total-beats counter were removed entirely (UI, state, persistence) — there is no click track or hit counter anywhere in the app now. Pad grid spacing was tightened from 8dp to 3dp to match a denser reference layout.

**Pad hit path** (the hot path — see `OctapadScreen.onPadHit()`): fires **synchronously**, not inside `scope.launch {}`, all the way through the native JNI trigger call. This is deliberate — wrapping the trigger in a coroutine used to add a silent ~16ms delay per hit (Compose's dispatcher defers `launch` to the next frame even from the UI thread). Only the "wait for playback to finish / loop again / update the LCD" bookkeeping after the trigger runs inside a coroutine, since that part doesn't affect what's actually heard. **Do not move the trigger call back inside a coroutine launch.**

**Loop logic gotchas** (`onPadHit()`'s `effectiveLoop()` and its wait/retrigger coroutine): whether a pad should keep looping depends on its *current* per-pad PLAY MODE and the *current* global LOOP toggle, both re-read live on every check — never capture either into a `val` before the coroutine's wait loop, since a loop can run for many iterations/seconds and a `val` snapshot goes stale, silently ignoring the user turning Loop off or switching PLAY MODE away from LOOP mid-playback (this exact staleness caused two real "loop won't turn off" bugs). The inner wait loop also breaks early — instead of always sleeping out the full tempo-synced `waitWindowMs` — the moment `loopTokens[index]` no longer matches this hit's token (superseded by a re-hit or a choke stop) or the moment effective-looping turns false (finishes out the sample's own `durationToShow` instead of the extra beat-sync padding). Per-pad PLAY MODE = LOOP is a true infinite hold, independent of the global toggle by design (documented in `DOCUMENTATION.md`) — the only way to silence one is a second tap on the same pad while it's holding (`loopModeActive` map tracks this), since there's no natural end to interrupt.

**BPM vs SPEED redesign (2026-09-02)**: per explicit request the two are now fully separate concerns. **SPEED** (LOOP panel) is a pitch/varispeed control — `onPadHit`'s `fire()` multiplies every voice's pitch by `speed.coerceIn(0.25f, 4f)` (so higher SPEED = faster + higher-pitched sample, exactly like the PITCH knob), and SPEED no longer appears anywhere in the loop-interval math. **BPM** is now the *only* input to the loop retrigger tempo: `beatIntervalMs = 60_000f / bpm` (floored 50ms), used for the global LOOP toggle. Per-pad LOOP mode stays a true gapless back-to-back repeat, retriggering on `durationToShow / speed` (divided because the sample now literally plays that much faster) — still never BPM-gated (beat-gating it reintroduces the old silence-gap bug). The `TempoPanel.kt` SPEED help text was updated to match. The pre-2026-09-02 notes below are the older fix history for when SPEED still scaled the interval.

**Multi-hit crackle on kit change ("khich khich jab patch badalke bajate hain")**: `AudioEngine::loadPadBuffer` now, under `bufferMutex_`, flags any voice currently playing the pad being reloaded as `releasing` *before* it `std::move`s the new sample into `buffers_[padIndex]`. Without this, a voice still sounding across a kit switch had its waveform swapped mid-playback and the next callback read a different sample from the same `v.position` — an instant amplitude jump = click. Fresh hits after the swap claim new voices and play the new buffer normally.

**BPM/SPEED fix**: two separate bugs, both fixed. (1) `beatIntervalMs` used to divide `60_000L / bpm` as `Long`, truncating to a whole millisecond *before* the SPEED division was ever applied (e.g. 127 BPM truncated 60000/127 to 472 instead of 472.44) — every subsequent SPEED scaling compounded that rounding. Now computed as `60_000f / bpm / speed`, truncated to `Long` once at the very end. (2) Per-pad PLAY MODE = LOOP used to always retrigger at the sample's raw `durationToShow`, completely ignoring the SPEED knob — the global Loop toggle's tempo-synced `beatIntervalMs` was (correctly) never applied to true LOOP mode (see the staleness/silence-gap note above for why), but nothing scaled LOOP mode's own interval by SPEED either, so testing SPEED against a PLAY MODE = LOOP pad (the common case) showed no effect at all. Fixed with a separate `loopModeIntervalMs = durationToShow / speed` used only for `currentMode == "LOOP"` — BPM still deliberately does not gate true LOOP mode, only SPEED scales it.

**Native audio engine** (`cpp/AudioEngine.h/.cpp`): Oboe stream opened Exclusive/MMAP when the device supports it (falls back to Shared automatically), device-native sample rate (deliberately not hardcoded — forcing a rate can make AAudio insert its own resampler), 1-burst buffer size for minimum latency, 24 pad slots (0–7/8–15/16–23 = Bank A/B/C), 64-voice polyphony pool.

The `Voice` struct has two atomics, `active` (slot-claim lock) and `ready` (safe-to-mix gate) — **this ordering is load-bearing, not a style choice**. `padIndex`/`position`/`volume`/`pitch`/`pan`/`gain`/`lengthFraction` must always be written *before* `ready` is set true, and the audio thread must gate on `ready`, not `active`. Getting this backwards reintroduces a real data race that previously caused audible stutter/double-triggering on fast multi-hits (the realtime audio thread could read a voice mid-write, using stale data from whatever note previously occupied that slot). `pan`/`gain` are new per-voice fields (equal-power pan law, multiplicative gain trim) applied in `onAudioReady`'s per-voice mix loop, following this exact same write-then-`ready` discipline.

**Multi-hit mixing / headroom**: `onAudioReady` sums all active voices with a headroom scale (`1/max(1, sqrt(activeVoiceCount))`) before clipping, and clips with `tanhf()` (a real soft-knee curve) instead of a hard `[-1,1]` clamp. Previously there was no headroom compensation and the "soft clip" was actually a hard clamp — stacking a handful of simultaneous voices pushed the sum past unity and produced audible harsh distortion on fast multi-hits. If you touch the mixing loop again, keep both parts: the headroom scale (so rapid multi-hits don't distort) and the `tanhf` soft-knee (so any residual overshoot rolls off smoothly).

**Voice attack fade-in — v1 reverted, v2 conditional (2026-08-18, same day)**: a per-voice `attackGain` fade-in (mirrors `releaseGain`'s fade-out, ramp 0.0→1.0 over ~3ms) was added to fix multi-hit crackle ("kich khich awaaz"). **v1 applied it unconditionally to every claim** — the next build had crackle on *every single tap*, including a lone hit starting from silence, a regression. Reverted entirely, then reintroduced **narrower (v2)**: `triggerPad`'s normal-claim and pool-exhausted-steal paths, and `fireDelayTaps`'s echo claim, now scan `voices_` for any other currently-`ready` voice at claim time — only if one exists (a genuinely concurrent/overlapping hit) does `attackGain` get armed to `0.0f`; a voice claimed into silence is set straight to `1.0f`, which is a no-op in `onAudioReady`'s mixing loop (`if (v.attackGain < 1.0f)` is false immediately, zero extra branches taken) — byte-for-byte the pre-attack-fade behavior for that case. This was **reasoned through, not verified on a physical device** (none available in this environment — see the root `CLAUDE.md`'s note on that); if multi-hit crackle is still reported after this build, or if a *new* single-tap regression shows up again, don't assume the conditional logic is correct just because it reads correctly — get an actual device test before iterating further blind.

**Voice-pool hygiene**: `AudioEngine::loadPadBuffer` rejects `sampleRate <= 0` outright, and both `triggerPad` and `setPadPitch` clamp `pitch` away from 0 — either being 0 makes `onAudioReady`'s playback rate 0, freezing a voice on frame 0 forever and permanently leaking it out of the shared 64-voice pool (never reintroduce an unguarded sample rate or pitch value on the write path). When the pool is fully exhausted, `triggerPad` steals the oldest currently-playing voice (tracked via each `Voice`'s monotonic `claimSeq`, bumped from `AudioEngine::voiceClaimCounter_`) rather than dropping the hit. `triggerPad`'s buffer-loaded check + stop-then-claim sequence, and `fireDelayTaps`'s buffer-loaded check, run under `bufferMutex_` (the same mutex `loadPadBuffer` writes under and `onAudioReady` reads under) — this is deliberately scoped so `bufferMutex_` is released before `delayMutex_` is taken in `triggerPad` (never nest them in that order), since `fireDelayTaps` takes `delayMutex_` first and `bufferMutex_` second from the audio thread; holding both in the opposite order from the calling-thread side would be a lock-order inversion.

**MIDI pad mapping is dual: note-based AND CC-based, both live.** An earlier pass's changelog claimed note-based pad mapping was "removed entirely" — that is no longer true (confirmed by a 2026-08-14 audit) and this doc previously said otherwise; treat any other doc/comment repeating the "CC-only" claim as stale too. `MidiLearnRepository` (note→pad map, persisted, survives restart), `MidiProcessor.cpp`'s `padToNote` map, `enableMidiLearn`/`assignMidiNote`/`getPadFromNote`/`getAllPadsForNote`, and the `onPadHit`/`sendPadToKotlin`/`onPadHitFromNative` JNI callback chain are all present and reachable — `MidiLearnScreen.kt`'s "PAD NOTES" section drives it, `OctapadScreen.kt` loads it on init, `BackupScreen.kt` includes it in export/import. **Separately**, `CcMapRepository`'s `PAD_1`..`PAD_8` targets provide an independent CC-based pad-triggering path through the same MIDI Learn flow used for Volume/Pitch/EQ/Patch-nav/etc. Either a learned note or a learned CC can fire a pad; there are no default CC-to-pad mappings (a freshly connected controller's pads fire via note-on only, until/unless a CC target is also learned). `MidiChannelState.selectedChannel` filtering (in `MidiReceiver.kt`) applies before Note, CC, and PC messages are dispatched.

**Factory vs. custom audio**: every pad's sound is either a factory `res/raw/kitN_padM.wav` resource (looked up via `kits[currentKit].sounds[padIndex]`, an `Int` resource ID, `-1` = none) or a custom `AudioItem` from `AudioRepository` (imported/recorded/edited). **Any feature touching pad audio must handle both** — `PcmMixer` (Mix/Add-To-End) and `WaveformEditorScreen` (crop editor) previously only checked `AudioRepository` and silently no-op'd on factory-only pads, which is the common case for most kits. The fix pattern (see `PcmMixer.resolvePcm()`) is: try `AudioRepository.audioForPad()` first, fall back to decoding the factory resource ID. Never resolve a factory resource ID by guessing from a kit's list position (`"kit${index+1}_padN"`) — kits get reordered/deleted/duplicated, so list position and factory kit number diverge. Always read the real ID from `kits[currentKit].sounds`.

**Choke redesigned: None/1/2/3/4, single level per pad, per-level folders**: `ChokePanel.kt` used to offer 6 choke levels with each pad free to belong to any subset of them (a multi-select toggle grid, one row per level showing all 8 pads). Now trimmed to levels None/1/2/3/4, and a pad belongs to at most ONE level at a time — picking a level for a pad is exclusive, like a dropdown, not a multi-select. `OctapadScreen.kt`'s `toggleChokeGroup(padIndex, level)` enforces this by clearing the pad's `chokeGroups[padIndex]` list before adding a *new* level, but only `remove()`s the specific tapped level (never `clear()`) when deselecting — storage is still `chokeGroups: List<SnapshotStateList<Int>>` (a list per pad) for backward compatibility with existing saved kits/backups, and a kit saved before this redesign could have a pad in multiple legacy levels at once (including 5/6, which have no UI anymore); `clear()`ing on deselect would have silently wiped every other legacy level too the first time that pad's UI-visible level was toggled off — a real data-loss bug caught in a post-implementation audit and fixed before it shipped. Going forward (kits touched after this fix) the list never holds more than one entry, so `remove()` and `clear()`-then-`add()` behave identically for those — the distinction only matters for pre-existing multi-level legacy data. The "CHOKE LEVELS" section is now 4 collapsible folders (Level 1-4) instead of one long list showing every level's full pad grid at once — collapsed, a folder shows which pads are currently assigned ("Pad 2, 5" or "No pads"); tap to expand and change that level's pads. The ACTIVE LEVEL row (which level is "live" for choking during play — a separate concept from per-pad group membership, see `chokesTogether()`) now also has an explicit NONE option alongside 1-4, instead of NONE only being reachable by tapping an already-active level to deselect it.

**RightPanel.kt's side panels all close through one `closeAllPanels()` helper**: every panel-opening path (CROP/CHOKE/DELAY row, FX/LOOP/SETTINGS row, DELAY icon's long-press, PATCH LIST) needs to force-close every *other* panel first, so a newly opened one is never left stacked underneath a stale one still showing. This used to be the same 5 lines (`showEqPanel = false; showMusicPanel = false; ...`) duplicated across 6+ call sites — every new panel added (DELAY was the most recent) meant hunting down and editing all of them, and the DELAY icon's long-press handler was found missing `activeBtn = "DELAY"` in a post-implementation audit (the panel opened correctly but the CROP/CHOKE/DELAY row kept highlighting whichever button was tapped last instead of DELAY). Add a new panel by adding one line to `closeAllPanels()`, not by touching every call site.

**MIDI/touch knob "stuck after testing for a while" + general latency**: the real cause was `persistKits()` — it JSON-serializes every kit slot (up to 200) synchronously — being called on **every single value change** from every continuous knob: VOLUME/PITCH/EQ CC handlers in `OctapadScreen.kt`'s `onControlChange`, and the matching on-screen VOL/PITCH/EQ/PAN/GAIN/DLY TIME/LENGTH sliders. A fast MIDI knob sweep can send dozens of CC messages per second; stacking a full-kits-list serialize+disk-write on every one of them, synchronously on the MIDI receive thread, made that thread fall further behind the longer a sweep continued — reads exactly as "the knob gets stuck." Fixed with `persistKitsDebounced()` (declared right after `persistKits()`): cancels/reschedules a `300ms` delayed save on every call, so continuous dragging/turning only writes once after it settles instead of on every tick. One-shot actions (rename, swap, delete, explicit SAVE, reverse/play-mode toggles) still call `persistKits()` directly — call sites need to be picked deliberately: something the user expects to survive an immediate app-kill (a toggle tap) should stay immediate, only genuinely continuous-drag values should go through the debounced path. Also removed `Log.d` calls that ran on every single MIDI message (`MidiReceiver.kt`'s Note On/Off/CC logging) and every pad hit (`onPadHit`'s `"PADHIT"` log) — each is a real syscall-level cost with no shipped-build benefit (ProGuard/R8 is disabled, so nothing strips debug logging from a release build either).

**Display cutout handling for "full screen on some phones, half on others"**: this app runs fully immersive (system bars hidden — `MainActivity.hideSystemBars()`) in landscape, but had no display-cutout (notch/camera-cutout) handling at all — `windowLayoutInDisplayCutoutMode` was left unset, so how a cutout got handled was purely down to each OEM's own default, which is not consistent, and part of the fixed pad-grid/control-panel layout could end up letterboxed out or drawn under the cutout on some phones. Fixed with two parts: `res/values-v27/themes.xml` sets `android:windowLayoutInDisplayCutoutMode="shortEdges"` (API 27+ only — a separate overlay file since the base `themes.xml` targets lower API too) so every device lets the app draw into the cutout area the same way; `OctapadScreen.kt`'s root `BoxWithConstraints` then adds `.windowInsetsPadding(WindowInsets.displayCutout)` so `maxWidth`/`maxHeight` (and therefore `controlPanelWidth` and every weighted child under it) are computed from the actual safe usable area, not the raw screen size — the real content never renders under the notch even though the app is still visually edge-to-edge everywhere else. If "half display" is still reported after this on a specific phone, get its exact model/Android version.

**Density remap (2026-09-02) — "har phone me display alag alag"**: `MainActivity`'s `fixedDensity` no longer passes the device's real density through. It computes `scaledDensity = realDensity * (currentScreenWidthDp / 820f)` and provides that via `LocalDensity`, so the usable screen is always exactly `820dp` wide regardless of the device's OEM default density or the user's "Display size"/"screen zoom" setting — every fixed-dp size in the instrument UI is now relative to one fixed design width and lays out identically across phones. Height still tracks the device aspect ratio (the existing `BoxWithConstraints` height-scaling in `OctapadScreen`/`RightPanel` absorbs that). `fontScale` stays pinned to 1x. If layout still differs across phones after this, it's an aspect-ratio/height-budget issue in a specific panel, not global scale.

**LinearSlider (VOL/PITCH/EQ/DLY TIME/DLY LEVEL/…) used to permanently stop responding to touch after enough use** — `RightPanel.kt`'s `LinearSlider` ran its drag handler as one bare `awaitPointerEventScope { while (true) { ... } }` for the composable's entire lifetime instead of one iteration per gesture. Every slider lives inside a `verticalScroll` panel (EQPanel/TempoPanel/DelayPanel/ChokePanel) — if a drag ever loses touch arbitration to that ancestor scrollable (ordinary with a slightly diagonal drag), Compose cancels the pointerInput coroutine, which throws out of the bare `awaitPointerEvent()` call uncaught. `pointerInput(min, max)` never restarts for a fixed-range slider, so that one cancellation permanently killed the slider — exactly the reported "volume/pitch knob gets stuck after a while of testing." Fixed by wrapping the loop in `awaitEachGesture` (the same pattern `WaveformEditorScreen.kt`'s canvas already used correctly), which absorbs a cancellation between gestures instead of dying. If the MIDI-driven path (CC → `kits[bankKitIdx()].volumes[...]` → `DrumEngine.setVolume()`) is still observed to stick after this fix, that's a separate, not-yet-diagnosed issue — get a repro that doesn't involve any on-screen touch first before assuming it's the same bug.

**MIDI `DELAY_TOGGLE` only-turned-on bug (fixed)**: the raw Note-On handler is installed once in `LaunchedEffect(Unit)`, so it captured `curPadDelayEnabled` (a per-recomposition `val`) at first composition — always `false` — and `setCurPadDelayEnabled(!curPadDelayEnabled)` therefore always set `true`, never toggling off. Now calls `toggleCurPadDelayEnabled()`, which re-reads the pad's live flag from `kits[bankKitIdx()].padDelayEnabled` at call time. Same stale-capture class as the `bankKitIdx()`-must-be-a-function note below.

**LOOP is per-kit + BPM now gates LOOP mode (2026-09-03, client override)**: the old global `loopEnabled` boolean is gone — replaced by `loopEnabledKits` (a `SnapshotStateList<Int>` of kit indices, persisted comma-separated as `KEY_LOOP_ENABLED_KITS`), read/written live via `loopOnForCurrentKit()` / `setLoopForCurrentKit()` (declared right after `bankKitIdx()`, which they depend on). Turning LOOP on affects only the active kit; a patch change stops the loop (the retrigger coroutine's `effectiveLoop()` re-reads `bankKitIdx()` every ~50ms), returning resumes it. Also, per explicit client request, the loop retrigger window is now `maxOf(beatIntervalMs, durationToShow / speed)` for **both** the global-toggle case and per-pad PLAY MODE = LOOP — this reverses the earlier "BPM deliberately never gates true LOOP mode" rule (see the older notes below). The `maxOf` floor means the sample is never cut mid-playback; the cost is a rhythmic gap when a short sample meets a slow BPM, which the client accepted. If you re-tune this, keep the `maxOf(..., audibleLen)` floor — dropping it is the "aawaz beech se cut" regression.

**SPEED is the only loop control now; BPM removed; varispeed removed (2026-09-07, client override)**: reverses most of the two notes above. Per explicit client feedback ("loop k liye bas speed rakhna hai", "loop mode me tempo kaam nahi krta", "speed me pitch change hota hai isko hata do sirf tone fast ho", "loop turant nahi pakadta"): (1) `fire()` no longer multiplies voice pitch by `speed` — SPEED is not a varispeed/pitch control anymore, voices play at their raw `kits[...].pitches[index]`. The two mirror sites that matched `fire()`'s old varispeed (`onControlChange`'s `PITCH` CC handler, the on-screen `onPitchChange` slider) push raw pitch too now. (2) The loop retrigger window is just `loopIntervalMs = durationToShow / speed.coerceIn(0.25f, 4f)` (floored 50ms), used for every looping case (`effectiveLoop()` true). No `beatIntervalMs`, no `maxOf` floor — SPEED > 1 deliberately cuts a long sample short (that IS "tone fast ho"), SPEED < 1 leaves a gap. (3) BPM is gone from `TempoPanel.kt` entirely (display + steppers removed; `bpm`/`onBpmChange` params dropped from `TempoPanel` and `RightPanel`). The `bpm` state var + `PreferencesRepository.loadBpm/saveBpm` + the backup `KEY_BPM` field are kept, unread by any UI, so old backups still parse. (4) The wait-loop poll tightened from `delay(50)` to `delay(15)` so a repeat fires within ~15ms of the sample ending. If a real pitch-preserving time-stretch is ever wanted, that's native DSP work — the client was offered it and chose the retrigger-rate approach instead.

**BPM restored, SPEED demoted to fine-tune, PITCH shown in semitones (2026-09-08, client override)**: partially reverses the note directly above ("BPM remove nahi karna tha, thoda thik karna tha"). (1) **BPM is back** in `TempoPanel.kt` — the display + `-10/-1/+1/+10` stepper row returned, `bpm`/`onBpmChange` re-threaded `OctapadScreen → RightPanel → TempoPanel`. (2) **SPEED is now a fine-tune multiplier around BPM**, not the whole loop control: its slider range is `0.9f..1.1f` (was `0.5..2`), and the loop math is `beatIntervalMs = 60_000f / bpm / speed.coerceIn(0.9f, 1.1f)`, then `waitWindowMs = maxOf(beatIntervalMs, durationToShow)` for every looping case — the `maxOf(…, durationToShow)` floor is back so a sample longer than one beat is never cut. `speed` is `coerceIn(0.9f,1.1f)` on load too (old wider persisted values snap in-range). (3) **SPEED still does NOT touch pitch** — the varispeed removal from the note above stays. (4) **PITCH is displayed as musical semitones**: `RightPanel.kt` has `pitchToSemitones` / `semitonesToPitch` / `semitoneLabel` (unity 1.00x = "C 0", ±12 st = 0.5x/2x), the PITCH `LinearSlider`'s `displayText` shows the note label, and a new `-10/-1/+1/+10` semitone stepper row (`PitchStepButton`) sits under the VOL/PITCH sliders — steps whole semitones, clamped ±12, live-updates via the same `onPitchChange`. (5) `delay(15)` poll from the note above is kept.

**New MIDI-Note action targets `FX` / `MASTER_DELAY` (2026-09-03)**: added to `NoteMapRepository.TARGETS` (MidiLearnScreen renders the list dynamically, so no UI change needed). `FX`'s panel open-state is `remember`ed *inside* `RightPanel.kt`, unreachable from `OctapadScreen`'s note handler — so `OctapadScreen` increments an `openFxPanelRequest` counter, `RightPanel` watches it with a `LaunchedEffect` and toggles the panel through `closeAllPanels()`. `request == 0` is skipped so nothing pops open on launch. `EDIT` already covers CROP (opens `WaveformEditorScreen`); `EDIT`'s handler now toggles `topPanel` instead of only setting it.

**`MASTER_DELAY` MIDI note toggles the kill switch, not the panel (2026-09-09, client fix)**: client reported "master delay paid ki button se on/off nahi hota, sirf per-folder wala hota hai" — correct: `DELAY_TOGGLE` flips only the selected pad's `padDelayEnabled`, and `MASTER_DELAY` used to just *open the DELAY panel* (`openDelayPanelRequest++`), nothing toggled the global `delayMasterEnabled` kill switch from MIDI. `MASTER_DELAY`'s handler now does `delayMasterEnabled = !delayMasterEnabled` directly (safe from the long-lived `LaunchedEffect(Unit)` note handler because `delayMasterEnabled` is a remembered `mutableStateOf` delegate, not a per-recomposition `val`). `openDelayPanelRequest` + its `RightPanel` `LaunchedEffect` are left in place (unincremented) in case a panel-open target is wanted later.

**BPM is a pitch-preserving time-stretch now, not just a retrigger gate (2026-09-11, client override)**: per explicit client request ("BPM me tone ki quality same rahe, sirf speed/duration badle" — contrasted with PITCH, which is expected to change tone character as it changes speed, that's the existing varispeed knob, untouched). `AudioEngine.cpp` gained a WSOLA (Waveform-Similarity Overlap-Add) time-stretch: `wsolaStretch()` (Hann-windowed overlap-add with a small correlation-search per frame to reduce phase-cancellation buzz), `AudioEngine::setPadLoopStretch(padIndex, ratio)` (copies the buffer under `bufferMutex_`, does the actual WSOLA pass **outside** the lock since it's real per-call CPU work, publishes into a new `stretchedBuffers_[padIndex]`), and a `Voice::useStretchedBuffer` flag (same write-before-`ready` discipline as every other Voice field) that makes `onAudioReady` mix from the stretched buffer instead of the raw one. `triggerPad`/`DrumEngine.trigger`/`NativeBridge.triggerPad` all gained a `useLoopStretch` param threaded through JNI. `OctapadScreen.kt`'s `fire()` computes `ratio = beatIntervalMs / durationToShow` (clamped 0.25x-4x) whenever `effectiveLoop()` is true and pushes it to native only when it changed since the last push for that native slot (`lastLoopStretchRatio` map) — WSOLA is real CPU work, don't call it every retrigger of an already-stable loop. The wait-loop's old `maxOf(beatIntervalMs, durationToShow)` floor (which existed only to avoid cutting a sample that had nowhere else to go) is gone — the sample now genuinely stretches to fit the beat, so the wait window is exactly the (same-clamped) stretched duration. Not verified by ear on a physical device (none available here) — only confirmed to compile/link (`compileDebugKotlin` + `externalNativeBuildDebug` + `assembleDebug` all pass).

**Denormal-float fix for "der tak bajane pe khich khich" (crackle after a long session), 2026-09-11**: the 3-band EQ's IIR filter states (`lpState_`/`bp1State_` in `AudioEngine.cpp`) run on every single audio callback unconditionally — even full silence — and between hits decay toward `0.0f` asymptotically, passing through (and lingering in) the denormal float range, which is a well-documented 10-100x-slower path on many ARM/x86 FPUs without flush-to-zero enabled. On the realtime audio thread that risks missing the callback deadline — heard as an intermittent glitch that gets more likely the longer/quieter a session runs, varying by device (denormal handling differs by CPU). This is the most likely explanation for the reported symptom. Fixed by snapping each filter state to exact `0.0f` once its magnitude drops below `1e-15f` (~-300dB, inaudible) instead of letting it keep decaying through denormal territory.

**Adaptive output-buffer sizing for device-inconsistent crackle (2026-09-11, client fix)**: client reported crackle present on some phones and not others ("sabhi device me sound same aaye").
